# ports/vala: Vala bindings for Simulant

`simulant-c.vapi` describes `libsimulant-c` (see `../c/`) to the Vala
compiler. It's generated by `tools/cgen/cgen.py --vapi` (on by default,
alongside the C generation) directly from the same IR the C emitter
consumes -- not by parsing the generated C headers separately -- so it's
guaranteed to describe exactly the C symbols that actually exist. Like
`ports/c/generated/`, it's committed to the repo: using it from a Vala
project needs nothing beyond `valac` and a linker, no Python/libclang/Vala
toolchain required just to *consume* it.

## Usage

```sh
valac --vapidir=ports/vala --pkg simulant-c your_program.vala \
    $(pkg-config --cflags --libs glib-2.0) \
    -X -Iports/c/generated/include -X -Iports/c/include \
    -X -Lbuild/simulant -X -Lbuild/ports/c \
    -X -lsimulant-c -X -lsimulant -X -lstdc++ -X -lm
```

(`valac` always needs GLib; Simulant itself doesn't use it, but every Vala
program's runtime does.) See `tests/smoke_test.vala` for a small worked
example, and `cmake --build . --target simulant-vala-check` for a
transpile-only regression check (requires `valac`; skipped otherwise).

## How the mapping works

- Every `smlt_x_t*` opaque handle becomes a `[Compact]` Vala class (a
  plain struct with manual memory management -- there's no GObject
  reference counting anywhere in this API, which is exactly what
  `[Compact]` models). `smlt_x_destroy`/`smlt_x_release`, when one exists,
  is set as the class's `free_function`, so a value going out of scope in
  Vala is cleaned up automatically, the same as any other Vala object.
  Classes with neither (e.g. abstract classes, `StageNode` subclasses --
  see `ports/c/README.md`) have no `free_function`; Vala never tries to
  free them, matching there being no safe way to do so mechanically.
- Enums map straight across, with each enumerator's real C name pinned
  explicitly via `[CCode (cname = "...")]` (not relying on `cprefix`
  stripping, since not every enum's members share a perfectly uniform
  prefix with the type name).
- Every method's first `self`-typed parameter is dropped from the Vala
  signature: Vala's default calling convention for instance methods
  already passes the receiver as the first C argument, which is exactly
  our convention, so this falls out for free.
- **Multiple constructor overloads**: only the first (by cgen.py's usual
  deterministic overload ordering -- see `tools/cgen/README.md`) becomes
  the bare `new ClassName(...)`. The others become *named* constructors,
  suffixed with whatever the underlying C function's suffix is -- the
  default numeric one (`smlt_vec3_create2` becomes `Vec3.overload2(...)`),
  or, if it was given a friendlier name via `tools/cgen/renames.json`
  (e.g. `smlt_color_create2` -> `smlt_color_create_from_array`), that
  suffix instead (`Color.from_array(...)`, not `Color.overload_from_array`
  -- the "overload" filler word is only added for the plain numeric
  case). Note this means the bare constructor is whichever overload
  cgen.py happened to order first (typically the fewest-parameters one,
  often a zero-arg default constructor), **not** necessarily the one you'd
  expect from
  argument count alone -- always check the class's constructors in the
  `.vapi` (or run cgen.py with `-v` and look at the warnings/skips) rather
  than guessing.
- Return types documented in `tools/cgen/README.md` as caller-owned
  (`needs_free_doc`, e.g. a by-value math type or a fresh `Asset`
  reference) map to plain `owned`-by-default Vala return types, so `var x
  = obj.method();` just works and Vala frees `x` automatically via the
  class's `free_function` -- **except** `string`, see below.
- Borrowed/non-owning pointer and reference returns (e.g.
  `Actor.base_mesh()`, most getters returning another object) are marked
  `unowned` -- Vala will not try to free these; the underlying object's
  real owner (the engine) is responsible for it.

### String returns need care

Every `string` return -- whether or not the underlying C function actually
transfers ownership (documented with a `/** Caller owns... */` comment
directly above the relevant method in the `.vapi`) -- is typed `unowned
string`, never plain `string`. This is deliberate, not an oversight:
methods that *do* hand over an owned string allocate it with
`smlt_c_strdup()`, which uses plain `malloc()`, not GLib's allocator.
Vala's ordinary `owned string` return semantics assume `g_free()`, which
would be a malloc/g_free mismatch.

The consequence: for a method documented as returning an owned string,
bind the result as `unowned string`, not `string` --

```vala
// WRONG: assigning `unowned string` to an owned `string` local silently
// makes a g_strdup()'d copy and leaks the original malloc()'d buffer.
string name = path.name();

// RIGHT: no hidden copy; free the actual buffer explicitly when done.
unowned string name = path.name();
stdout.printf("%s\n", name);
Smlt.free_string((void*) name);
```

For a method *not* documented as transferring ownership, just use the
`unowned string` as-is and don't call `free_string()` on it (the engine
owns it).

## Known gaps

- **`ports/c/include/simulant/c/*_ext.h` (`stage_node_ext.h`,
  `scene_ext.h`, `application_ext.h`) are not covered.** These are
  hand-written C, not produced by cgen.py's scan of the C++ sources, so
  they're outside what `--vapi` generates from. Subclassing `StageNode`,
  `Scene`, or `Application` from Vala today means declaring their vtable
  structs and `extern` functions by hand in a small supplementary `.vapi`
  snippet (or callbacks via `[CCode (cname = "...")] public delegate ...`
  bound directly to the vtable field types) -- not done yet.
- Every class lives in a single flat `Smlt` namespace (`Smlt.UiWidget`,
  not `Smlt.Ui.Widget`) -- a mechanical PascalCase of cgen.py's own flat
  `ui_widget`-style C base names, not a re-derived C++ namespace tree.
- `Smlt.Path` shadows Vala's implicit `GLib.Path` -- reference it as
  `Smlt.Path` explicitly if you also have `using Smlt;` in scope and hit
  an "ambiguous reference" error.
